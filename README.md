# Grunderna i Git

## Fråga 1: Versionshantering vs vanliga filer

**_Vad är versionshantering och vad är den stora skillnaden mellan att spara en fil via editorns vanliga sparaknapp och att spara ändringar i Git?
Förklara vad som menas med att Git sparar en tidslinje av frysta ögonblicksbilder (commits). Vad bevisar det faktum att du när som helst kan klicka på din allra första commit på GitHub och fortfarande se alla tre TODO kvar i koden, trots att filen på din dator ser helt annorlunda ut idag?_**\
Versionshantering innebär att man kan ta ögonblicksbilder av en eller flera filer för att följa förändringar över tid. Detta gör det möjligt att gå tillbaka för att granska eller återgå till tidigare versioner, samtidigt som man undviker att skriva över andras arbete. Den största skillnaden mellan att spara en fil via editorns sparaknapp och att spara ändringar i Git är att man vid det senare tillvägagångssättet – genom att förbereda (stage) och sedan bekräfta (commit) ändringarna – arkiverar olika versioner. När man däremot sparar en fil lokalt på vanligt sätt, skriver man över den befintliga filen varje gång man sparar.
En "tidslinje av frysta ögonblicksbilder" innebär att Git kan liknas vid en kamera med hög precision för ditt projekt; varje gång du gör en `commit` fångas eller fryses ett specifikt ögonblick. Att man kan komma åt en tidigare version – till exempel en tidig TODO – trots att ändringar gjorts senare eller filer raderats från datorn, visar att commits är oföränderliga och att arbetskatalogerna är oberoende av varandra. När en ögonblicksbild väl har sparats genom en `commit`, skrivs den in i historiken med ett unikt ID – en så kallad hash – och kan därefter aldrig ändras eller uppdateras; den är alltså oföränderlig. Utöver denna oföränderlighet innebär det också att du kan se dina senaste ändringar i ditt nuvarande arbetskatalog, samtidigt som Git och GitHub lagrar alla de ögonblicksbilder (commits) som skapats under projektets gång.

## Fråga 2: Arbetsytan, Staging och Commits ##\

**_Beskriv vad kommandona `git status`, `git add` och `git commit` gör i det dagliga arbetsflödet och när du kör dem.
Förklara relationen mellan arbetsytan (arket på skrivbordet), staging (kuvertet) och commit (arkivlådan). Förklara också varför Git protesterar med `no changes added to commit` om man har ändrat filen i editorn och försöker köra `git commit` direkt utan `git add`._**\
`git status` skannar ditt projekt och visar en sammanfattning av skillnaderna mellan dina nuvarande filer och din senaste `commit`. Kommandot visar vilka filer som har ändrats, vilka som är nya (”untracked”) och vilka som är förberedda (”staged”) för nästa sparning. Det bör köras ofta – både före och efter att du förbereder filer – och kan liknas vid en kompass som visar var du befinner dig i förhållande till din senaste `commit`.
`git add` används för att välja ut nya eller ändrade filer som ska inkluderas i nästa `commit`. Detta görs när du har slutfört en mindre, sammanhängande uppgift – som att åtgärda ett fel, skriva en funktion eller uppdatera en stilmall – och vill förbereda (”staga”) dessa ändringar inför nästa `commit`. `git commit` sparar de ändringar du förberett med `git add` som en kronologisk ögonblicksbild i din Git-historik; detta kräver ett beskrivande meddelande som förklarar varför ändringen gjordes. Kommandot används när ett logiskt steg i ditt projekt har slutförts.
Arbetsytan kan liknas vid ett pappersark på skrivbordet; det är den aktiva mappen där koden skrivs. Den representerar nuet – en plats där man kan klottra, sudda och skriva om. Staging (förberedelse) kan i förhållande till arbetsytan liknas vid ett kuvert. Det är en förberedelsezon där du tar kopior av vissa delar från papperet på skrivbordet och lägger dem i ett öppet kuvert. En `commit` kan liknas vid en arkivlåda: när du utför ett `git commit` förseglar du kuvertet, stämplar det med datum, tid och en beskrivning, och placerar det i en låst arkivlåda. Väl inne i lådan (i commit-historiken) kan innehållet varken ändras eller gå förlorat.
Git protesterar med `no changes added to commit` eftersom det inte är logiskt att arkivera ett tomt kuvert. Även om ny kod har skrivits på ”pappersarket” (arbetsytan), måste ”papperet” först läggas i ”kuvertet” (staging) innan det kan placeras i "arkivlådan" (commit-historiken). `git commit` tittar enbart i staging-området för att avgöra vad som ska arkiveras.

## Fråga 3: Lådan hemma vs Montern på GitHub

**_Vad är skillnaden mellan mappen på din dator och repot på GitHub, och vad gör kommandot `git push`?
Förklara konceptet med de två rummen / minnesytorna (lådan hemma på datorn vs glasmontern på GitHub). Förklara varför `git push` svarar `Everything up-to-date` om du har ändrat i koden men glömt att staga och committa innan du kör push._**\
Mapparna på din dator utgör din lokala arbetsyta. De ändringar du gör här är helt privata och finns bara på din egen dator; de riskerar alltså att gå förlorade vid hårddiskfel eller om de raderas. Däremot finns arkivet (repositoryt) på GitHub säkert lagrat i molnet. Det fungerar som en central källa för ögonblicksbilder av ditt projekt över tid, och andra kan få tillgång till det om du tillåter det. Kommandot `git push` fungerar som en bro mellan dessa två miljöer: det laddar upp dina lokala ändringar (commits) till det fjärrliggande arkivet på GitHub. Om vi ​​tänker oss användaren som en konstnär, kan det lokala arkivet (Git-databasen) liknas vid en trälåda i din ateljé. När du gör en `commit` packar du ner målningen i lådan, där den är skyddad och undanlagd. Det fjärrliggande arkivet (GitHub) kan i sin tur liknas vid ett museum där målningen ställs ut, så att allmänheten eller dina samarbetspartners kan se den.
Om du ändrar kod i editorn och kör `git push`, kommer Git att visa meddelandet `Everything up-to-date`, trots att koden på din skärm ser helt annorlunda ut än den som finns på GitHub. Om vi ​​använder liknelsen med en målare beror detta på att `git push` inte tittar i editorn; den tittar bara inuti "trälådan". När du kör `git push` jämför Git den senaste incheckningen (commit) i din lokala "trälåda" med den senaste incheckningen som finns i GitHubs "museet". Om du har gjort ändringar men glömt att köra `git add` och `git commit`, ligger dessa nya ändringar kvar i din "ateljé" (din arbetskatalog). Om målningen (ändringarna) aldrig packas ner i lådan (det lokala arkivet), kan den inte skickas till museet (GitHub). Git analyserar de två lagringsplatserna, ser att den lokala lådan och museet på distans stämmer exakt överens, och rapporterar därför – utifrån sitt spårningssystem – att "allt är uppdaterat". För att åtgärda detta måste du först köra `git add .` för att förbereda ändringarna (stage), och därefter `git commit` för att spara dem i din lokala låda, innan du utför en `git push`.
